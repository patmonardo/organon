# GraphFrame Intelligence: Dataset as SDSL Builder (Speculative)

Date: 2026-08-04
Status: Speculative Doctrine Reference

This reference states a speculative but guiding thesis:

Dataset is the generative form that builds domain language (SDSL), and GraphFrame is the first high-level application species that this builder is meant to produce.

The goal is not to freeze implementation details. The goal is to stabilize orientation so implementation can evolve without losing rationale.

---

## Task Framing

Layer:

- Kernel: executes graph and table bodies with empirical discipline.
- Agent: orchestrates reflection, planning, and intervention.
- Logic: states why the resulting mediation counts as knowledge.

Target:

- empirical adequacy (Kernel)
- conceptual validity (Agent)
- rationale coherence (Logic)

Invariant checks:

- empirical adequacy
- reflexive consistency
- dialectical mediation

## Core Thesis

A Dataset in this system is not only a bag of rows. It is a semantic builder with explicit form logic.

Compactly:

Dataset + Form Logic -> SDSL Builder -> GraphFrame

GraphFrame is therefore not an accidental extension. It is a determinate realization of Dataset intelligence at application level.

---

## Three Substrates of the Builder

The Dataset SDSL builder carries three coupled substrates:

- structural substrate: Frame, Series, Expr
- semantic substrate: Model, Feature, Plan
- rational substrate: Corpus, LM, Logic

This triadic structure allows the same authored intent to become multiple runtime bodies without semantic loss.

---

## Feature Scope Doctrine

Graph is a model type and has model-scope features that are irreducible to local scopes.

Keep three feature strata explicit:

- Graph Features: whole-graph properties and constraints.
- Node Features: per-node determinations.
- Edge Features: per-edge determinations.

Graph Features must remain first-class and must not be collapsed into node or edge fields.

---

## Why GraphFrame Is the Right Species

GraphFrame is the first suitable intelligence API for two co-equal tasks:

- rational mediation of GraphStore operations
- constitution and execution of graph analytics jobs

This pairing matters. If GraphStore mediation and analytics execution are separated into unrelated surfaces, model intent fractures and provenance weakens.

---

## Relation to DataFrame

DataFrame remains necessary and valuable as executable tabular substrate.

But DataFrame alone is not the end form. Dataset names and mediates; DataFrame executes; GraphFrame realizes graph-operational intelligence for application work.

A short lineage:

1. DataFrame phase: practical execution body.
2. Dataset phase: semantic and epistemic articulation.
3. GraphFrame phase: high-level graph intelligence framework.

## Evaluative Norms for Evolution

Any Dataset -> GraphFrame extension should remain reviewable by these questions:

1. Does it preserve empirical adequacy at execution surfaces?
2. Does it preserve reflexive consistency between authored intent and emitted artifacts?
3. Does it preserve dialectical mediation across model, feature, and plan?
4. Does it keep Graph Features first-class at model scope?
5. Does it keep provenance legible from GraphStore operation to analytic output?

If these fail, the extension is not a valid SDSL realization even if fit metrics improve.

## Stage Gates for GraphFrame Adoption

Treat GraphFrame adoption as gated progression, not wholesale migration.

Gate 1: Language Gate (Logic target)

- Graph feature grammar is explicit and distinguishes Graph, Node, Edge scopes.
- Form logic states valid transformations and prohibited collapses.

Gate 2: Mediation Gate (Agent target)

- Program-level intent compiles through a legible GraphForm path.
- Explanations remain stable under replay of the same intent.

Gate 3: Execution Gate (Kernel target)

- Compiled intent runs through existing Task/Shell surfaces.
- Empirical behavior is testable and comparable to baseline procedures.

Gate 4: Service Gate (Applications target)

- GraphStore operations and graph analytics outputs remain provenance-legible.
- TS/JSON surfaces stay stable while internals evolve.

Only after all four gates pass should any GraphFrame path be considered doctrinally promoted.

---

## Failure and Rollback Conditions

A GraphFrame increment must be rolled back or quarantined if any of the following appear:

1. Graph Features are implicitly reduced to node/edge-only attributes.
2. Shell procedures thicken to compensate for missing GraphFrame intelligence.
3. Provenance is broken between GraphStore mediation and analytic outputs.
4. Reflexive consistency degrades (same intent yields unstable conceptual reading).
5. Empirical adequacy regresses against known baselines without rationale gain.

Rollback is a methodological success condition, not a project failure.
